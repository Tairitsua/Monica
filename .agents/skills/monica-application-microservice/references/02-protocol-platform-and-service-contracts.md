# Contracts in split deployments

[Unified architecture](../../monica-application/references/03-unified-architecture.md) owns Protocol, role metadata, Host generation and runtime placement. Keep requests in `Platform.Protocol.PublishedLanguages.Domain{Domain}.Requests`; a role split does not add a purpose suffix to that namespace or generate an interface per role.

The single ApiEndpoint owns each operation's HTTP mapping. Protocol emits stable domain interfaces. A generated lightweight catalog carries shared ownership without runtime implementation references; each Host generates callers and receivers for its actual local handlers. Compose AddApplicationModel, AddApplicationRpc and the HTTP provider needed by omitted implementations, constrained operations or authority destinations. Do not use a whole-domain AppId dictionary as the authority for operations owned by several roles.

Ordinary operations prefer Local when their implementation is included. Otherwise a published operation uses its catalog owner and placement. RunOnRole belongs on the request only when execution requires that role's resources or authority; do not add it merely because another artifact omits the implementation. Its owner must agree with the handler role. HTTP ingress requires an included handler and active role; the receiver executes locally without forwarding. Required receivers remain available in Release builds.

An independently hosted server UI can use the build-generated catalog without backend implementation references, or retain supported explicit HTTP caller generation. Define authentication propagation explicitly. Catalog generation is a build-time source-owned contract, not arbitrary runtime manifest loading. Private multipart ingress remains with its implementation and existing gateway route. gRPC is unsupported. See [RPC registration](../../monica-infra-messaging/references/rpc.md) and [application invocation](../../monica-application-ui/references/application-invocation.md).
