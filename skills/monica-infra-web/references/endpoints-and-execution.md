# Request endpoints and execution

The execution-pipeline UI formats its plan-capture timestamp with the shell's shared Clock display policy in `$monica-infra-ui` (`references/time-display.md`); the catalog's captured instant and pipeline behavior are unchanged.

## Typed CRUD services

Derive a resource from `Monica.WebApi.AutoControllers.Services.CrudService<TEntity, TKey, TDetail, TRow, TQuery>`. Inject the scoped EF store through the constructor and include the concrete service in the host's type discovery. The base implements `ICrudApplicationService`. Its `ToDetailAsync` hook converts a visible entity to a detail DTO, which can be immutable. `ReadRowsAsync` reads one keyed row per entity from the ordered query window. A generated projection or handwritten `Select` can run in SQL. A local converter can enumerate the EF entity window with the supplied cancellation token and yield the converted rows in order.

```csharp
[Mapper(RequiredMappingStrategy = RequiredMappingStrategy.Target)]
public static partial class MapperStockItem
{
    public static partial StockItemDetail ToDetail(StockItem entity);
    public static partial IQueryable<StockItemRow> ProjectRows(IQueryable<StockItem> query);
}

public sealed class CrudServiceStockItem(StockItemRepository repository)
    : CrudService<StockItem, int, StockItemDetail, StockItemRow, CrudPageRequestDto>(repository)
{
    protected override Task<StockItemDetail> ToDetailAsync(StockItem entity, CancellationToken ct)
        => Task.FromResult(MapperStockItem.ToDetail(entity));

    protected override IAsyncEnumerable<StockItemRow> ReadRowsAsync(IQueryable<StockItem> window, CancellationToken ct)
        => MapperStockItem.ProjectRows(window).AsAsyncEnumerable();

    public Task<Result> UpdateAsync(int id, RenameStockItem input)
        => UpdateEntityAsync(id, item => item.Rename(input.Description), QueryCancellationToken);
}
```

Declare the mapper in the owning domain core and call it from the role's concrete CRUD service. Keep updates that enforce an invariant on the entity, as in `Rename`. For Mapperly-generated mappings, reference `Riok.Mapperly` in the project declaring the mapper and call its projection from `ReadRowsAsync`. Use `RequiredMappingStrategy.Target` and add `RMG012` to the project's `WarningsAsErrors` so newly added response members require an explicit mapping decision. Check the generated projection against the deployed EF provider. [Mapperly projections](https://mapperly.riok.app/docs/configuration/queryable-projections/) · [Mapperly diagnostics](https://mapperly.riok.app/docs/configuration/analyzer-diagnostics/)

`CrudPageRequestDto` supplies filtering, search, sorting, field selection, and pagination. A narrower `TQuery` enables the features expressed by its implemented request interfaces. With default conventions, `GetAsync(id)` binds `GET {resource}/{id}`, `GetListAsync(input)` binds `GET {resource}` from the query string, `ListAsync(input)` binds `POST {resource}/list` from the body, and `ListStreamAsync(input, cancellationToken)` binds `POST {resource}/list-stream` from the body. The CLR prefix `CrudControllerOption.ServiceNamePrefix` defaults to `CrudService`. Both the derived controller name and the default Building Blocks convention use it. When moving from a suffix convention, rename the service and verify the API resource and verbs against the previously published routes. Use `id` for the conventional key route token. The built-in read actions declare transaction mode `None`. HTTP reads use `RequestAborted`, and a stream's `CancellationToken` is execution context. Enumerate streams inside the DI scope that owns the repository.

The page actions wrap `Page<dynamic>` in a `Result`. They return full `TRow` objects or [ModelQuery](model-query.md) properties selected through the request. Distinct field pages sort and count the selected tuples before applying the offset. Sorting accepts selected field names or aliases and their direction. Remaining tuple members break ties. Distinct tuples use offset paging. When the count is skipped, the page reports the number of items read. Selected pages carry items and count with null navigation metadata. Offset ordering uses the entity key to break ties where needed. An entity cursor is the last row key. A key-only sort seeks in its requested direction. For a composite sort the provider continues after the visible anchor row in the same order, including tie-breakers. A missing composite anchor yields an empty continuation. Validate key ordering with the deployed provider and include the key in any projection that offers continuation.

`CreateFilteredQueryAsync` composes the store's visibility filters, includes, resource filters, and ModelQuery terms. Supply another scoped store for a history table when appropriate. `ReadPageAsync(input, filtered, ct)` returns the raw typed page. The overload with a named `IQueryable<TEntity>` projection returns the alternate row type and derives its cursor when that type exposes the entity key. `ReadFieldPageAsync(input, filtered, selection, ct)` reads the explicit selected shape. For sharded queries, pass the selection to `ApplySorting` only when executing selected fields. Fixed-row callers can retain selections for their own use, such as export headers. The standard page calls `EnrichPageAsync` once on a nonzero full-row page after the reader closes. Preserve row identity and order when replacing items. Failures retain their status, message, and metadata. The stream yields a bare JSON array, applies `MaxResultCount`, and preserves repeated rows. Use the page actions for offset paging, totals, distinct selection, and enrichment.

Declare the public actions for the resource's supported writes. The default verbs and routes follow `POST {resource}` for `CreateAsync`, `PUT {resource}/{id}` for `UpdateAsync`, `DELETE {resource}/{id}` for `DeleteAsync`, and `POST {resource}/bulk-delete` for `BulkDeleteAsync`. Construct a valid entity before calling `InsertEntityAsync`. It requires the current execution transaction and flushes to obtain the key for the acknowledgement. `UpdateEntityAsync` loads through the tracked detail query and invokes the supplied mutation once. Validate any body key against the route key before changing the entity, preserve its identity and protected members, and apply concurrency preconditions through the repository. `DeleteEntityAsync` stages the repository's removal policy and acknowledges an already absent row. `DeleteEntitiesAsync` stages policy-aware removal for the supplied keys. The surrounding [execution transaction](../../monica-infra-persistence/references/transactions.md) owns commit and rollback.

See [API documentation](api-documentation-and-visibility.md#crud-collection-responses) for collection schemas and alternate DTO actions. The relational HTTP and repository contracts are exercised in `tests/Test.Monica.WebApi/AutoControllers/ModelQueryCrudIntegrationTests.cs`.

## Role-owned endpoint admission

Application-model HTTP admission keeps generated receiver actions and role-owned MVC routes discoverable on an assigned, quarantined role. Their requests receive the host's configured 503 result envelope after authorization and before model binding or controller activation. Actions in the same generated controller can belong to different roles. Inactive MVC role routes continue to be omitted. A runtime quarantine takes effect on the next admission and lets requests already executing finish. The refusing MVC or Monica Minimal API gate increments `monica.application.role.quarantined_requests` with `transport=http` once. See [role metrics](../../monica-infra-observability/references/opentelemetry-metrics.md#application-role-isolation).

Minimal APIs mapped with the module's `UseEndpoints` helper or marked with `WithMonicaEndpoint()` also gate the role-owned handler before parameter binding. The role comes from the handler type or the owning Monica module contribution. A host with the result-envelope module receives its configured error envelope. See [startup fault policy](../../monica-infra-hosting/references/application-model.md#startup-fault-policy).

## Transport-independent application calls

Transaction-enabled execution entries attach their descriptor and invocation ID to `ExecutionScopeContext` for [first-failure diagnostics](../../monica-infra-persistence/references/transactions.md#first-failure-diagnostics). Same-provider nested entries restore their parent's metadata; independent scopes start without the caller's operation metadata. This captures operation identity without retaining request inputs or changing rollback policy.

HTTP failure statuses and handled MVC exceptions do not automatically request rollback. The outermost transaction commits on normal completion regardless of the response status; use the [business-outcome and explicit-abort contract](../../monica-infra-persistence/references/transactions.md#business-outcomes-and-explicit-abort) when a failed response must roll back writes.

`ApplicationRequestHandler`, `DomainService`, and the `IQuery`/`ICommand` result contracts are owned by `Monica.Application.Abstractions`; request validation is in `Monica.Application.Validation`. `AddWebApi()` composes `AddApplication()` for the shared mediator, authorization and DataAnnotations validation path. `AddApplication()` alone publishes no HTTP endpoints. Standard authorization no longer requires a permission-bit enum; use `AddAuthorization<TEnum>` only for that model.

Native request handlers return `Result` or `Result<T>` through explicit factories. Paged CRUD methods return `Result<Page<dynamic>>`, with page data on success. Use `Result.Success(data)` for data, `Result.Success().WithMessage(message)` for a no-data message, and `Result.FromFailure<T>(source)` for failure forwarding with metadata intact. For construction, nullable payloads, supported statuses, and pagination, see `$monica-development` (`references/result-type-guide.md`). HTTP adapters use `IResultEnvelope` and `GetResponse()`. Keep envelope and HTTP statuses consistent. Refresh generated clients when adopting the new result types and review how they handle absent page data on failure.

`Monica.Application.Annotations.ApiEndpoint(ApiHttpMethod, route)` declares the application operation and its HTTP mapping in one attribute. Local and HTTP clients share this declaration; carrying HTTP metadata does not publish endpoints. Each `[assembly: ApplicationHost]` combines shared ownership metadata where used with its actual local domain/role implementations to generate its manifest and clients. Receivers come only from local implementations; `AddApplicationModel` validates deployment ownership and `AddApplicationInvocation` routes each operation. Standalone consumers can still use `ApplicationApiGenerationConfig` and optional `WebApiGenerationConfig`. Optional assembly-wide `HttpApiContract` settings customize the shared prefix. See [API generation and registration](../../monica-infra-messaging/references/invocation.md) for configuration, ownership and migration.

Unattributed requests remain internal mediator operations. Local API calls default to Shared: they join an active logical UnitOfWork or create a fresh operation scope when none exists, including inside a `None` orchestration. Generated APIs expose immutable `WithTransaction(ApiTransaction.Independent)` views for operations that must complete separately from an active parent. Query defaults follow the explicit `IQueryRequest` contract (including `IQuery<TData>` and POST/internal queries), not naming or HTTP verb; explicit handler transaction metadata may request a read-only consistency transaction. MVC binding remains separate from application validation. See application invocation in `$monica-application-ui` (`references/application-invocation.md`) for UI identity and lifecycle rules.

With `AddApplication`, every business execution entry establishes its borrowed DI scope in the host-owned `ExecutionScopeContext`, including mediator, EventBus and explicit business pipeline calls; disposal restores the parent on success, failure and cancellation. Explicit UnitOfWork calls also establish their owning scope. Adapters select the scope before resolving handlers, enter new scopes before initializing collaborators, and await work before disposal. The context does not own that service provider. `ExecutionScopeContext.GetActiveUnitOfWorkServices` distinguishes an active logical UnitOfWork from an ambient execution scope, using the optional scoped `IExecutionTransaction` contract without a Repository dependency. It rejects completed work rather than restarting it. New scopes for nested Shared calls retain exception propagation; allocating a scope does not establish a result-presentation boundary. Bare execution pipelines retain their allocation-free no-behavior path. `Shared` rejects remote dispatch while a physical local transaction is active; see the [transaction contract](../../monica-infra-persistence/references/transactions.md#shared-and-independent-api-calls) for logical/physical state and custom transaction-owner requirements.

For role-local request contracts outside `PublishedLanguages`, the generator derives the wire domain from the declaring assembly's `ApplicationRole`. An explicit `HttpApiContract.DomainName` takes precedence when retaining an existing wire name. An assembly without role metadata still needs the explicit name; a non-identifier domain also needs a valid explicit generated name. This inference changes no declared HTTP method or route.


Inside the host's `builder.AddMonica(monica => { ... })` callback, `AddAutoControllers(configure?, configureCrud?)` discovers `ControllerBase` types and `ICrudApplicationService` implementations from the configured type-discovery scope, validates CRUD options, registers generated MVC conventions, and maps controllers. It depends on ModelQuery, the core controller module, and exception handling; `AddWebApi()` already requires it. Application request contracts own their `[ApiEndpoint]` method, route, and binding metadata. The reference app puts those attributed requests in `Platform.Protocol/PublishedLanguages` and adds that assembly to type discovery. For request naming, controller placement, and endpoint ownership, read `$monica-application-building-block-development`.

When a controller or generated route is missing, check that its assembly is discovered, that its service shape is eligible, and that its CRUD naming/suffix matches configured conventions before manually adding routes. Invalid CRUD options fail service composition with `OptionsValidationException`. Inspect the generated API description and [Swagger document assignment](api-documentation-and-visibility.md) if the route exists but is missing from the chosen document.

With an application model, generated request receivers require a local implementation and are selected per action from their owning role. An inactive role's action is removed before MVC constructs endpoints, including when the same controller contains methods from other roles. Ordinary included handlers remain callable locally; RunOnRole requests additionally require their role at execution. Remote-only operations do not publish forwarding receivers. CRUD services and hand-written controllers in inactive role assemblies are likewise excluded from ingress. This filtering does not remove unrelated framework controllers.

For a host containing several local domains, configure `AddAutoControllers(configureCrud: options => options.RoutePath = "api/v1/{domain}")`. The literal `{domain}` token expands using the concrete controller assembly's declared role or domain core, yielding routes such as `api/v1/Ordering/order`. It is not a caller-supplied route value or the current host's single domain. An unowned controller using this token fails endpoint composition. Explicit controller Route attributes still override the global prefix. The default prefix remains `api/v1/[controller]` for standalone compatibility.

`AddModelQuery()` registers model snapshots, field-name resolution, filtering, fuzzy matching and projection for IQueryable or in-memory sources. Read the dedicated [ModelQuery contract](model-query.md) for field annotations, QueryNames, option inheritance, source-shape services and diagnostic routes.

The Building Block domain-event tester uses the shared JSON editor in `$monica-infra-ui` (`references/json.md`) for its event draft. Formatting and syntax feedback do not publish events; its explicit Publish command retains the framework serialization, deserialization and dispatch behavior.

Business HTTP endpoints follow request-owned metadata and execute through the shared typed execution pipeline. `AddBuildingBlocks()` owns architecture discovery and requires EventBus. Business projects declare Building Block context metadata using `Monica.ApplicationModel.Annotations`; see `$monica-application-building-block-development` (`references/03-building-block-context-metadata.md`). Its `/framework/building-blocks` inspection routes are opt-in through `EnableMinimalApi = true`, or the host-wide `EnableMinimalApiByDefault`; the UI uses the facade directly and does not require those HTTP routes. The optional request filter is off unless `EnableRequestFilter` is selected. The pipeline is also used outside HTTP: authorization and execution timing install filtered behaviors for business operations. Do not bypass it with a second ad hoc controller path for the same request contract.

To group diagnostics by the pipeline boundary, pass the descriptor’s `OperationKey` to `ExecutionOperationKey.ReadIdentity(key)`. The returned point and component preserve the length-prefixed identity, including separators embedded in a component name. A direct timing scope or an incomplete key returns `null`. Use the complete operation key to identify an aggregate.

Runtime and source catalogs discover `ApplicationRequestHandler<TRequest, TResponse>` and associate its request with the exact complete response type: `Result`, `Result<TData>`, or an adopted custom response. `ResponseType` never means only the result payload. Concrete project specializations retain this association through their native base. Native `IRequest<TResponse>` contracts and `IResultRequestBase` both participate in request building block discovery. The non-generic `ApplicationService` common base alone is not a request handler; CRUD remains a separate kind through `ICrudApplicationService`. Keep the request in the host's discovery scope; classification does not approve the application's architecture.

Both catalogs classify `IDistributedBatchEventHandler<TEvent>` and the `DistributedBatchEventHandler<TEvent>` EventBus base as distributed-event handler building blocks, retaining the `DistributedEventHandler` naming prefix, constructor dependencies and event association. Their execution point is `eventbus.distributed-batch-handler`; the `monica-building-blocks-source/v1` contract identifies the source observation format. Transaction attributes belong on `HandleBatchAsync`, not on a separate single-event method. Follow the event-handler template in `$monica-application-building-block-development` (`references/14-event-handler-template.md`) and [batch receive contract](../../monica-infra-messaging/references/event-bus.md#explicit-batch-consumers) for adoption. Runtime/source parity is covered by `tests/Test.Monica.BuildingBlocks.CodeAnalysis/Services/BuildingBlockSymbolClassifierParityTests.cs`.

Building Blocks includes closed generic event payloads and request contracts referenced by discovered handlers when their generic definitions are also in the discovery scope. Open generic definitions are not catalog units. Each closed type retains its full CLR identity, metadata, and links to its consumers; a missing or excluded contract definition still produces an association warning. Event payloads must implement `IDomainEvent`; application event conventions remain owned by the Building Block development skill.

Declare a transaction override or database selection only with `ExecutionTransactionAttribute` on the concrete handler/action method; the execution descriptor resolves that declaration for every adapter. Use the persistence [transaction contract](../../monica-infra-persistence/references/transactions.md) for defaults, automatic saving, and independent operation scopes.

`AddExecutionPipeline()` can be registered directly when a host needs typed execution without the Web API bundle. `.AddBehavior<TBehavior>(order, descriptorFilter, lifetime)` adds one implementation to the host-owned catalog; filters decide which descriptors receive it. The same behavior type registered twice fails composition, and behavior service registrations are checked for exclusivity. Use `ExecutionPipelineCatalogFacade` to inspect the effective behavior plan when an expected authorization, timing, or custom behavior is absent. Route generation and execution behavior are related but distinct: first confirm endpoint discovery, then confirm the request reaches the pipeline.

For a Web host with a Monica shell, `AddBuildingBlocksUI()` exposes the discovered architecture catalog and requires Building Blocks, localization, and the shell. `AddExecutionPipelineUI()` presents the effective behavior catalog and requires the pipeline, localization, and the shell. These are optional inspection pages; their access policy belongs to `$monica-infra-ui`, and neither page is required for HTTP request execution.

`AddBuildingBlocksUI()` registers six independently routed pages in the shell's Monitor → Building Blocks branch. The `/building-blocks` address opens the Overview page.

Configuration details report Startup values as requiring restart even when their consumers use `IOptionsSnapshot<T>` or `IOptionsMonitor<T>`, or no consumer is discovered. These accessors all return the same frozen Startup object. Managed configuration alone uses accessor-based reload inference; see the configuration unit contract in `$monica-application-building-block-development` (`references/16-configuration-template.md`).

The catalog’s full-identity dossier is a native modal with a localized visible heading that names its actual dialog role. It uses the shared dialog heading contract in `$monica-ui-development` (`references/blazor-best-practices.md#14-native-dialog-headings`); keyboard focus and dismissal remain native. Opening the dossier reads captured evidence and does not execute the selected unit.

Each page has its own shell/search name and title. The shared workspace links are real routes, so direct navigation and browser Back/Forward identify the task. Leaving a page disposes its local view; returning creates a fresh view with newly loaded data, local filters, selection, graph, or draft. No cross-route page session, storage, or polling is introduced. Host-owned catalog data remains independent of those page lifetimes. The route split adds no backend API endpoint or access policy; existing facade operations and host configuration retain their contracts.

Refresh reads the host's discovered catalog rather than rescanning assemblies or executing units. The catalog presents Title and full Key together, retaining the complete identity for search and inspection. Its full-key sort control cycles unsorted → ascending → descending → unsorted through the native grid's multiple-sort API; removing the Key sort preserves any other active sort. Name sorting retains the native grid's multiple-sort behavior. The four context coverage dimensions have independent covered/total denominators and an undefined percentage for an empty catalog; they are not runtime health or a combined readiness score. The relationship workspace's connected-component scope traverses both dependency directions and overrides ordinary filters until cleared. Enum positions are enumeration-order indices, not numeric enum values.

Graph cursor actions retain the exact admitted unit and full Key across asynchronous work. Each right-click establishes a distinct opening, including repeated clicks on the same unit at the same coordinates; late completion cannot close a replacement menu or render into a retired graph. The native unit ledger supplies equivalent actions, and copying the full name preserves the complete Key. Custom graph integrations follow the shared cursor-menu contract in `$monica-infra-ui` (`references/shell-and-access.md`) for opening revisions, page coordinates, native focus and lifetime ownership.

Domain-event descriptors from `BuildingBlocksFacade.GetDomainEventsAsync()` expose `BuildingBlockDomainEventInfo.EventKey`, the exact full CLR identity used for publication. Pass that value to `PublishDomainEventAsync(eventKey, payload)` or the existing `/framework/building-blocks/domain-event/{eventKey}/publish` route; do not derive it from the friendly title. Full identity is resolved before unique short names, so equal short names in different namespaces remain independently publishable. Short keys work only when unique across the catalog; ambiguous names are rejected without publishing, and `IBuildingBlockCatalog.FindByName` returns null. Equal short names in distinct domains or closed generic constructions are valid and do not themselves produce discovery errors. Selecting a descriptor only creates an editable representative payload; Publish deserializes the supplied JSON with this host's serializer and performs a real distributed EventBus operation. It is not a simulated preview, and page disposal does not cancel a publication already dispatched to the bus. Select the host's intended provider explicitly as described in [Web composition](web-composition.md).

`BuildingBlocksFacade.GetRequestFilterStateAsync()` reads a detached host-local snapshot containing `IsAvailable` and `DisabledPaths`. An unavailable service differs from an available service whose disabled-path set is empty. Availability establishes service registration only: it does not prove middleware attachment, endpoint authorization, or universal request access. `EnableRequestFilter` defaults to false; when enabled, `UseMonica()` attaches the module's middleware. Paths are ordinal and case-sensitive, duplicates are idempotent, and enabling one path changes the actual host-local filter. `ManageRequestFilterAsync(urls, disable)` retains its existing mutation/read contract and returns an empty list when no service is registered; use the new read method when that distinction matters. The UI names each path action explicitly and disables mutation controls for an unavailable service. Neither facade introduces a new permission policy or changes endpoint exposure.

An event without a public parameterless constructor, such as a positional record, remains in the event catalog with a null representative `Structure`; enter its actual JSON payload when publishing. Sample construction does not invent constructor arguments. Nested abstract or constructor-bound types and recursive references are represented by null so one valid event shape does not prevent inspecting the rest of the catalog.

The `/execution-pipeline` page distinguishes observed plans from the complete candidate-registration catalog. Snapshot queries inspect cached metadata; they do not execute an operation or construct missing plans merely to populate the page. Ready/Faulted and plan timestamps describe chain materialization, not a business invocation result or duration. The selected plan shows actual outer-to-inner positions and closed behavior types separately from configured registration order and registered types. Behaviors can short-circuit the terminal handler. A successfully materialized plan with no behaviors still has a terminal handler; missing behavior metadata on a faulted plan does not establish a terminal-only chain. An excluded candidate has no recorded per-plan exclusion reason. Refresh preserves filters and reconciles selection by stable plan ID. Exact expandable/copyable diagnostics retain full identifiers and available policy, source, lifetime and fault evidence rather than replacing them with abbreviated display names.
