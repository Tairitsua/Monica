# Developing the shared Guide engine

Use this reference when changing Guide implementation or product release contracts. Ordinary installation and workspace operations use the executable commands described in the skill.

- `Monica.Guide.Engine` owns the shared setup behavior for Monica agent products. `Monica.Guide.App` packages the per-platform wizard and CLI. Neither is a NuGet product.
- `KnownAgentProducts` owns each product's release contract. Consumers such as Monica.Workflow select their definition and reuse the engine; they do not maintain a second implementation of Guide behavior.
- `skills/monica-guide` teaches and routes to the engine. Do not put a local implementation of engine setup logic or scripts in this skill.
- `.monica/agent-skill-catalog.json` owns managed instruction templates, source repositories, and aliases. `scripts/build_monica_guide_bundle.py` projects them into release bundles; edit the canonical catalog rather than a generated bundle.
- The bundle also projects canonical profile `required`, `recommended`, and capability-conditioned roots into `profileSelections`. Guide expands selected roots through required dependency edges; skill-level recommendations do not recursively widen the installation. Workspace configure, release refresh, inspection, and setup preview counts use the same selector and the workspace's confirmed capabilities. Products with unconditional profiles, such as Workflow, can retain per-entry profile membership.
- Managed instructions live in `AGENTS.md`. Initialization and workspace configure remove only the current product's well-formed legacy span from `CLAUDE.md`, preserving user and sibling-product content and the minimal `@AGENTS.md` import when Claude is selected globally or through `.claude/skills`. Malformed or duplicate product markers block the entire plan before apply.
- Guide manages Monica framework skills and source lookup. Monica.Docs is an ordinary checkout with no Guide-specific profile, source binding, or instruction injection.

## Standalone wizard presentation and runtime ownership

Guide.App is an Interactive Server application with native HTML controls, local fonts, its own light/dark theme, and the `SetupSession.T` language catalog. It does not compose Monica.UI modules or the framework Appearance service. Keep app palette definitions in `Monica.Guide.App/wwwroot/css/themes/guide`, shared wizard controls in the app stylesheet, and shell/page composition in their owning isolated styles. Preserve the `mw-setup-theme` storage key. The theme control names its next action and reads the actual DOM mode after interactive startup; language changes also update the document language through the app-owned shell helper.

The shell skip link keeps its same-document `#guide-main` fragment fallback. Interactive activation additionally focuses the connected, programmatically focusable main landmark and scrolls it into view through a named app helper. Guard the dispatch against layout retirement and a changed route, and observe/log failures; changing the fragment alone does not establish keyboard focus movement. Compact grid rows use their content height rather than stretching sparse pages to fill the viewport.

Overview paints structural installation facts before joining the facade's full diagnosis. Installation presence and loopback process state are separate from diagnostic severity. Preserve the persisted host observation and its explicit re-detection action. The facade owns warmup and host detection across route changes; a disposed page stops adopting results and callbacks without canceling that shared work. Setup mutations still belong to the engine's digest-locked preview/apply flow, while policy preferences and Windows conveniences save immediately.

For an isolated source preview, override both `MONICA_GUIDE_DATA_ROOT` and each product's `MONICA_GUIDE_PRODUCT_DATA_ROOT_*` in the child process. Configure preview DataProtection persistence separately under a disposable task-owned directory. These overrides do not redirect global skill roots, arbitrary workspace paths, Windows shortcuts/autostart, or update staging beside an installed bundle. Begin with empty isolated state and keep write controls inactive until their actual targets are contained. Use the app's supported wizard arguments (`--product`, `--port`, `--no-open-browser`), retain its per-run `/s/<token>/` admission boundary, and require an interactive native-control response after navigation; an untokened 404 or a listening marker alone does not establish UI readiness.

## Application UI selection

Keep `application` as the product profile. Backend architecture (`microservice` or `modular-monolith`) is independent of UI inclusion. Absence of `ui` means backend-only; selecting `ui` adds `monica-application-ui`, `monica-application-ui-development`, and their required shared UI mechanics. The catalog owns this closure. The wizard presents Backend only / With application UI, preserves recorded capabilities when editing an existing application, and uses the same preview/install selector as the CLI. Do not install framework module architecture merely because a business application includes UI.

CLI examples: `init --workspace <path> --profile application --capability modular-monolith` for backend-only; add another `--capability ui` for business UI. Existing workspace configurations without `ui` retain backend-only semantics; reselect the application choices to adopt UI. Selection does not create a separate frontend deployment or a second project specification.
