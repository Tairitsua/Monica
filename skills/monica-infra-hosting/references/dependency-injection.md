# Conventional dependency injection and decoration

`monica.AddDependencyInjection()` opts the host into service registration by convention. Concrete classes implementing `ITransientDependency`, `IScopedDependency`, or `ISingletonDependency`, or marked with `DependencyAttribute`, are candidates only when their assembly is in the configured type-discovery scope. Put the marker on an application service with the intended lifetime, then include its assembly through `ConfigureTypeDiscovery(...)` inside the same `AddMonica(...)` callback. Monica also registers `ICachedServiceProvider`; this is a module service, not a reason to bypass ordinary scoped DI.

`ServiceBase` in `Monica.DependencyInjection.Abstractions` supplies `Logger` and `Mapper` to conventionally activated scoped or transient services. Use them in service methods after activation assigns the cached provider. `Logger` uses the concrete service type as its category, and `Mapper` resolves the host's registered `IObjectMapper`.

If a marked service is missing, check the assembly selection, whether the class is concrete, and the marker or attribute before manually adding a duplicate descriptor. `monica.AddDependencyInjection().EnableAutoRegistrationDiagnostics()` captures a startup snapshot and declares the hosted-service dependency for that capture. `EnableAutoRegistrationLogging()` separately controls per-type startup logs; it is disabled by default even when the snapshot is enabled. Inspect `DependencyInjectionDiagnosticsFacade` or the startup output for registration decisions.

For a Web host with the Monica shell, `monica.AddDependencyInjectionUI()` enables diagnostics and exposes two related routes:

- `/dependency-injection` shows conventional registration findings and the final collection in registration order. Follow a takeover or missing registration into the implementation drawer. A selected tape range opens Service resolution filtered to identities with a descriptor in that range.
- `/dependency-injection/services` groups descriptors by exact service type and key. The latest descriptor of an identity supplies the matrix cell and the registry row. Open the row to see earlier descriptors in collection order and follow links to related conventional exposures. Filters and evidence selections are shareable in the URL.

Refresh re-reads the process-lifetime snapshot and normally retains the materialization timestamp. Export snapshot downloads the captured data for comparison across hosts or releases. The workbench inspects registrations without resolving services, invoking factories, or validating their constructor graphs. Registration order describes the exact registered identity. Runtime fallback for an unregistered closed generic or a wildcard key requires the container's own lookup.

The registrar records forwarding and cached-provider activation explicitly. `IsDirectConventionMatch` identifies descriptors the registrar actually created. An inferred match uses service identity, lifetime and implementation when the original descriptor is absent. `ServiceIdentityIndex` is local to one snapshot and distinguishes unequal keys even when their display text is the same.

The page keeps convention issues separate from registry results because an issue can concern a source type that produced no descriptor. Warning/error counts describe convention diagnostics, not host health. Search covers service/implementation/assembly/key and available convention, exposure and issue metadata. Source and lifetime selections OR within their group and AND with the other groups; special markers OR keyed/warning/error matches, while Standard means none of those markers. An empty selection matches nothing; Reset restores all choices. The registry supports multiple-column sorting and paged inspection, and retains its grid while refreshing an existing snapshot. Details expose exact identities and available implementation metadata before convention mode/outcome, lifetime source, exposed services and attached issues; Escape, Close and backdrop dismiss the inspector.

There is no current production `ModuleDynamicProxy` or `AddDynamicProxy()` registration in Monica DI/Core. The remaining public interface-proxy decorator extension, `IServiceCollection.DecorateInterfaceProxy<TInterface,TDecorator>()`, is in `Monica.Experimental`, which is included in the solution but is not a Monica module. It decorates matching registered interfaces; the non-`Try` form throws `DecorationException` when none is registered, while `TryDecorateInterfaceProxy` returns `false`. Treat this as an explicit experimental DI choice, not an automatic effect of `AddDependencyInjection()`. For execution-wide behavior use the typed execution pipeline; for a local wrapper, choose decoration after checking the service lifetime and interface contract.

Verify discovery and diagnostics against `Monica.DependencyInjection/Modules/ModuleDependencyInjection.cs` and `Monica.DependencyInjection/Services/ConventionalRegistrar.cs`. For graph and host lifecycle, read [host composition](host-composition.md); for module strategy design and type discovery internals, read `$monica-development`.
