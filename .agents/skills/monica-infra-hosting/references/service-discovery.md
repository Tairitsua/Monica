# Service discovery

Select the role and storage mode inside the host's `AddMonica(...)` callback:

```csharp
builder.AddMonica(monica =>
{
    monica.AddServiceDiscovery()
        .AsStandalone()
        .UseMemoryStorage();
});
```

The role defaults to `Worker`: it registers and runs workloads without owning registry control-plane duties. `AsRegistry()` assigns registry duties; `AsStandalone()` combines registry and worker on one host. A storage mode is mandatory even for the default worker. `UseMemoryStorage()` is process-local and fits a single process; for multiple instances, select a shared store. `UseDistributedStorage()` requires a distributed provider selected on `ModuleStateStore`. `UseExternalKeyedStorage(key)` requires an existing keyed `IStateStore` registration under that exact key; there is no unkeyed fallback. Composition validates the storage choice and its service contract.

The module requires hosted services, localization, and a retry pipeline. Its `ServiceDiscoveryClientHostedService` owns registration and exposes `IServiceRegistrationCoordinator`; `ServiceDiscoveryFacade` provides scoped status queries. Optional registry-status and leader endpoints are mapped only on Web hosts when the Minimal API switch permits them, while worker services run on generic hosts. The role and storage choice are independent: changing a worker to a registry does not select a store. Identity options such as `AppId`, `DomainName`, and `AppName` fall back to `ConfigureApplication(...)` defaults; `IncludeListeningAddresses` defaults to `true`. `SkipRegistrationWait` defaults to `false`, and `RegistrationWaitTimeout` to five minutes, so inspect registration state when a dependent scheduler appears delayed.

After startup, inject `ServiceDiscoveryFacade` and call `GetServicesStatusAsync()` for registered service status, or `GetMergedServicesStatusAsync()` for the merged operational view. Use `GetDomainsAsync()` followed by `GetDomainDetailAsync(domainName)` to inspect a particular domain. Check each returned `Res<T>` before reading its data. If an expected instance is missing, compare its configured identity and selected storage with the querying host, then inspect registration readiness; a separate in-memory store cannot see another process. `GetRegistryLeaderStatusAsync()` helps distinguish missing registration from absent registry leadership. These queries inspect discovery state; use the messaging skill's [API reference](../../monica-infra-messaging/references/invocation.md) for making an application call.

For configuring the underlying distributed or keyed provider, read [state-stores.md](state-stores.md). Verify role, contracts, registration services, and defaults in `Monica.ServiceDiscovery/Modules/ModuleServiceDiscovery.cs`, and query contracts in `Monica.ServiceDiscovery/Facades/ServiceDiscoveryFacade.cs`.

## Address and environment metadata

With `AddApplicationModel`, the default client reports `RoleIds` and `DomainNames` from this AppId's selected roles. The legacy singular `DomainName` is populated only when exactly one domain is active. Its AppId must agree with the application model. Per-instance registration and detached snapshots preserve these lists; the merged service view reports the union of observed instance roles/domains, so inspect individual instances during mixed-version rollouts. Domain detail queries, filters, service lists, and domain graphs include every observed owned domain. The inspector reports observed roles independently of process readiness. `GetDomainNames()` includes legacy singular evidence during mixed-version rollout; do not reduce multi-domain membership to the first domain.

The default catalog combines registered domains with the compiled application model and derives predefined AppIds from its deployment map. Custom catalog providers can retain display labels, but should reuse the model's identities. `DependentSubDomains` remains an explicit legacy relationship; the model does not infer the exact runtime call graph from every referenced assembly.

`IncludeListeningAddresses` collects the host server's `IServerAddressesFeature.Addresses` into listening-address metadata. To include a process environment variable in full client metadata, add its name to `ModuleServiceDiscoveryOption.MetadataEnvironmentVariables`. `DefaultServiceDiscoveryClientInfo.GetServiceStatus(isHeartbeatInfo: false)` reads those environment variables when constructing the full result; it does not cache them in its constructor. Heartbeat-only results omit this metadata. The registration manager explicitly requests the full result for both initial registration and subsequent heartbeats because each store write replaces the complete registration record.

For a Kubernetes NodePort publication, follow the [K8S NodePort publication contract](../../monica-infra-ui/references/k8s-workspace.md#publish-the-current-services-nodeport-addresses). The default output key is `K8S_LISTENING_ADDRESSES`; the K8S initializer does not add it to service-discovery configuration automatically. Preserve or add that key in `MetadataEnvironmentVariables` and, when using the service-discovery UI, in `ModuleServiceDiscoveryUIOption.DisplayMetadataKeys`. Changing the publication output key requires updating both consumers. This external-address metadata is separate from the host server's actual bound listening addresses.

K8S publication runs in the background, so the first registration may precede the address value. The next heartbeat after successful publication reads the current environment and includes the addresses in the full replacement record; later heartbeats continue including them. `ElectionConfig.HeartbeatPeriodSeconds` defaults to `15`. A delayed or failed Kubernetes query does not hold up host startup.

## Captured diagnostics and provider reads

For interactive diagnostics, `CaptureServicesAsync(cancellationToken)`, `CaptureDomainsAsync(cancellationToken)`, and `CaptureCurrentInstanceAsync(cancellationToken)` return detached evidence in `Res<T>`. Failed reads return an error, rather than a successful empty capture; log details remain on the host. The built-in registration manager propagates registration-enumeration and leader-read failures. A custom manager or catalog provider must also distinguish failed reads from successful absence. The store must support registration-key enumeration: a provider that cannot scan keys produces a diagnostic failure rather than an empty registry. The catalog interface has no cancellation argument; captures drain its read and then reject canceled results.

Unexpired `reg:{AppId}:{InstanceId}` entries establish membership in the selected store. The merged view maps them to `Running`; this does not represent a readiness or health probe. Predefined services without registrations remain `Offline`. Their catalog contract supplies identity only, so diagnostics must not invent subdomain or build evidence for them. Version, build, heartbeat and configured metadata displayed at service level come from one observed registration; inspect individual registrations when those values differ.

The independent `leader:{AppId}` lease identifies the stored application leader. A registration's `IsLeader` flag is heartbeat-reported and can lag the lease. Current-host diagnostics show election participation only for `Registry` and `Standalone`; `Worker` does not participate. Local election state and configuration describe the querying host, even while an inspector shows another service. UI-observed disappearances are retained circuit observations, not provider eviction records or a durable cluster history.

Force-delete removes the selected application's leader key; it does not remove registrations or stop a process, and a host may acquire a new lease on a later heartbeat. The existing UI and optional Minimal API authorization remain host-owned. Lease-generation fencing and qualified graceful release are separate backend concerns; a captured UI inspection does not guarantee that leadership remains unchanged when a mutation executes.

The service and domain graphs retain the exact selected service/domain for each cursor-menu opening. Each admitted right-click has its own opening revision, even at the same coordinates; completing an older action cannot dismiss a newer menu or update a retired graph. The native roster Actions remain an equivalent entry point. Domain inspection and navigation to a catalogued subdomain are separate actions: an unlisted domain still supports inspection, but does not gain a catalog route. Integrations use the shared [cursor-menu contract](../../monica-infra-ui/references/shell-and-access.md), including document/page coordinates and native menu ownership; these UI lifetimes do not change discovery capture or provider lifetimes.
