# Module registration and runtime contracts

`Describe(ModuleDescriptor)` declares `Require<TModule,TOptions>()`, `AfterIfPresent<TModule,TOptions>()`, and `RequireFeature(...)` without reading finalized options. `Require(..., configure)` may contribute defaults to the dependency. Normal module options are finalized and validated dependency-first before their service callbacks. A module reads its own `Option`; it may use `GetOptions<TModule,TOptions>()` only for a direct hard dependency and `TryGetOptions<TModule,TOptions>()` only for directly declared optional ordering.

The single application authority implements `IApplicationCompositionModule`. After the user callback and the initial dependency descriptions, Core finalizes that authority's options once, applying dependency defaults before host contributions. `PrepareApplication` compiles its model and may call `MonicaApplication.ProjectApplicationIdentity` to project the selected deployment's name. Core then freezes identity and discovery, and `RegisterApplication` declares owned services and modules while the builder is still open. Newly added modules receive their dependency descriptions before the final graph seal. The authority's options and lifecycle are not replayed. Adding a second authority, changing the prepared authority, or recursively executing registration fails composition. Preparation does not read other modules' options or resolve services.

ApplicationModel runs each declaration through `Composition.RunRegistration(declarationType, callback)`. Framework APIs capture `Composition.RegistrationOwner` per contribution or resource. Module registration handles retain that origin independently from the dependency-default ordering owner; option/profile callbacks, service and Web contributions, startup work and serial commits, and finalization callbacks restore it when they execute. `ModuleCompositionContext.RegistrationOwner` exposes the captured origin. A shared module's own lifecycle is unowned, so its resources must retain their individual declarations. Descriptor ownership is recorded without invoking factories, including hosted services added during finalization. This metadata does not gate passive application services.

Module phases run on a serial control plane. `ScheduleStartupWork(...)` is for isolated synchronous work scheduled from `ConfigureBuilder`, `ConfigureServices`, a type-discovery commit, or `PostConfigureServices`; choose its barrier deliberately. Work queued from a discovery commit is already past `BeforeTypeDiscovery`. `BeforeHostLifecycle` and `NoBarrier` cannot have a serial service-registration commit. Use Generic Host lifecycle hooks for asynchronous work.

Keep runtime state owned by the module, exposed through a module-owned singleton or internal registry when several phases need the same instance. A builder-extension closure or mutable options object is not a reliable store: transitive registration must have the same baseline behavior as direct `Add*()` registration. Do not hide mandatory services, middleware, endpoints, or post-configuration in the convenience extension.

Framework extensions that must share state before DI use `IMonicaCompositionContext.Composition`, the same `MonicaCompositionState` exposed by the builder, module composition context and `MonicaApplication`. `GetOrAdd<TState>` creates one host-owned state per type; recursive creation fails, and new state cannot be added after finalization. The extension owns any disposable resources it creates. `StartupConfiguration` is an immutable, shape-aware source snapshot captured before the user callback; `LiveConfiguration` retains accepted reloads and later projections. Never construct a temporary service provider or flatten the snapshot through `AsEnumerable()` to implement an early typed reader.

`Composition.OnServicesFinalized(complete, validate)` registers framework completion and an optional final invariant check after all module service phases and the `BeforeServiceRegistrationCompletion` barrier, before service-contract validation. All completion callbacks run first and may install final adapters; then every validation callback receives the same read-only descriptor snapshot. Neither pass may resolve services, add modules or register more hooks. Validators must not mutate registrations. The callbacks run once. This validates composition through the return of `AddMonica`; arbitrary later changes to the raw service collection are outside that boundary. Configuration installs frozen accessors during completion and rejects conflicting options contributions during validation, including contributions from later completion callbacks.

The configuration owner installs `Composition.ValidateEnvironmentFiles` once its definition inventory is complete. It validates each selected file independently, including lower-priority values hidden by another provider, before a candidate replaces the last accepted values and shapes. Use `ConfigurationSourcePathException` for a controlled path-only rejection; other callback exception messages are withheld from reload diagnostics. This callback must not bind runtime services or write a shared store.

Configure host assembly scope once with `monica.ConfigureTypeDiscovery(options => options.Add(...).Exclude(...))`; `ExcludeDefault()` is appropriate only when the host supplies the complete scope. A module declares structural `TypeQuery` matches through one `DeclareTypeDiscovery(TypeDiscoveryPlan<TOptions>)` override. Monica analyzes all non-empty plans over one type universe, then commits in graph and declaration order after ordinary registration and before `PostConfigureServices`. A non-empty query still commits with zero matches. Use the commit context's indexed `Registrations` writer for high-volume registrations; do not retain temporary reflection matches unless runtime behavior owns them.

When a discovered contract definition is closed by another discovered type, `BusinessTypeShape.MakeGenericType(typeArguments)` returns a cached closed structural shape owned by that definition. It rejects arguments that remain open. This does not expand any module's discovery matches: the consuming module owns the derived relationship and must retain the original discovery scope, including exclusions. Factory-only infrastructure helpers should declare `[ExcludeFromBusinessTypeDiscovery]` when they must not participate in any module's business queries.

If a module uses `IStringLocalizer<TResource>`, declare `ModuleLocalization` as an intrinsic dependency in `Describe(...)` and contribute the resource marker there. Keep marker classes and JSON under project-root `Localization/`. Inject localizers into DI-created types; static helpers receive a localizer argument or delegate formatting to an injected formatter. Use `ILocalizationCatalog` for genuinely generic lookup. Do not introduce ambient localization state.

`ModuleDiagnosticsFacade.GetSnapshot()` gives a cached immutable composition view per revision. Load assembly inventory and option details only when needed. `CreateExport()` omits option values, assembly paths, stack traces, and raw exceptions. Mark secret options with `[ModuleOptionDiagnosticsSensitive]` or `ConfigureModuleOptionDiagnostics(...MarkSensitive(...))`. `RevealSensitive` is a Development-only, uncached bounded-scalar view and never changes the sanitized export. Startup budgets report measured thresholds only when configured.

Operational pages are automatic in Development. Elsewhere they inherit `ModuleShellUIOption.OperationalPageAccess.AuthorizationPolicy`, with page overrides where needed. `OperationalPageAccess.DebugMode` bypasses authorization in every environment; `ModuleUIHostOption.EnableDebug` instead controls detailed Blazor and SignalR errors. Keep these decisions separate.
