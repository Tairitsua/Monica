# Service discovery

With `Application:AutonomousWork=false`, service discovery retains registry queries and the canonical application catalog, but does not construct its registration worker or register, heartbeat, elect, renew or delete shared membership state. `IServiceRegistrationCoordinator.IsRegistered` stays false and its wait returns false immediately for this intentional nonparticipation. The native state manager rejects mutation methods in this mode, including explicit leader deletion. APIs that require real registration must report that unmet prerequisite.


Instance registration and outbound endpoint resolution are independent modules in the same `Monica.ServiceDiscovery` project, which also contains their UI. Membership requires a store; endpoint resolution does not. Invocation can also run Local or ordinary HTTP without enabling either module.

Select the role and storage mode inside the host's `AddMonica(...)` callback:

```csharp
builder.AddMonica(monica =>
{
    monica.AddServiceDiscovery()
        .AsStandalone()
        .UseMemoryStorage();
});
```

The role defaults to `Worker`: it registers and runs workloads without owning registry control-plane duties. `AsRegistry()` assigns registry duties; `AsStandalone()` combines registry and worker on one host. A storage mode is mandatory even for the default worker. `UseMemoryStorage()` is process-local and fits a single process; for multiple instances, select a shared store. `UseDistributedStorage()` requires a distributed provider selected on `ModuleStateStore`. `UseExternalKeyedStorage(key)` requires an existing keyed `IStateStore` registration under that exact key; there is no unkeyed fallback. Composition validates the storage choice and its service contract.

The module requires hosted services, localization, and a retry pipeline. Its `ServiceDiscoveryClientHostedService` owns registration and exposes `IServiceRegistrationCoordinator`; `ServiceDiscoveryFacade` provides scoped status queries. Optional registry-status and leader endpoints are mapped only on Web hosts when the Minimal API switch permits them, while worker services run on generic hosts. The role and storage choice are independent: changing a worker to a registry does not select a store. Standalone hosts retain module identity overrides with `ConfigureApplication(...)` fallbacks. With an application model, the canonical current AppId and its deployment entry's AppName are authoritative; conflicting module overrides fail composition. `IncludeListeningAddresses` defaults to `true`. `SkipRegistrationWait` defaults to `false`, and `RegistrationWaitTimeout` to five minutes, so inspect registration state when a dependent scheduler appears delayed.

After startup, inject `ServiceDiscoveryFacade` and call `GetServicesStatusAsync()` for registered service status, or `GetMergedServicesStatusAsync()` for the merged operational view. Use `GetDomainsAsync()` followed by `GetDomainDetailAsync(domainName)` to inspect a particular domain. Check each returned `Res<T>` before reading its data. If an expected instance is missing, compare its configured identity and selected storage with the querying host, then inspect registration readiness; a separate in-memory store cannot see another process. `GetRegistryLeaderStatusAsync()` helps distinguish missing registration from absent registry leadership. These queries inspect discovery state; use the messaging skill's [API reference](../../monica-infra-messaging/references/invocation.md) for making an application call.

For configuring the underlying distributed or keyed provider, read [state-stores.md](state-stores.md). Verify role, contracts, registration services, and defaults in `Monica.ServiceDiscovery/Modules/ModuleServiceDiscovery.cs`, and query contracts in `Monica.ServiceDiscovery/Facades/ServiceDiscoveryFacade.cs`.

## Leadership authority and lifetime

Membership records remain in the selected StateStore. Election and leader queries use `IExclusiveLeaseStore` and the shared `LeaseCoordinator`, not StateStore ETags or `leader:` keys. Distributed and external membership require `.UseLeaderLeaseStore(serviceKey, scope)` with an existing keyed singleton authority, including on worker/query-only hosts. Memory membership defaults to an isolated in-process lease store. See [lease provider selection](leases.md#provider-selection-and-redis) for Redis registration, connection ownership and namespace isolation.

The role name is `service-discovery:<AppId>` within the selected scope; the holder is the instance ID. Default `LeaderTTL` remains 31 seconds. Renewal runs independently every third of that TTL; `Election.LeaseStandbyInterval` defaults to five seconds and `LeaseOperationTimeout` to five seconds, strictly below `LeaderTTL / 3`. Heartbeat failure or expiry of the last successful registration stops participation. A blocked heartbeat cannot extend the local lease deadline. Worker-role hosts never acquire a leader role.

`ILeaderElectionService.CurrentLease` exposes the current immutable term and stopping token. `CurrentTermId` replaces `CurrentETag`; acquisition time does not change on renewal. Every reacquisition emits a new gained event after the previous term's loss, including reacquisition by the same instance. Never refresh a mismatched ETag or continue old work under a new grant. `LeaderGainedEvent.Lease` and `LeaderLostEvent.Identity` identify these lifetimes.

`CoordinatedLeaderService` links initialization and background work directly to the term token. It serializes transitions and drains old work/cleanup before starting another term. Implementations must cooperate with cancellation; an elapsed cleanup timeout is not evidence that old work stopped. Normal resignation/shutdown stops renewal and leaves the grant to expire, because arbitrary event subscribers cannot be proven drained by the election service. Takeover can therefore wait the remaining TTL. The explicit administrative force-delete action uses the provider's separate `ILeaseAdministration` capability; it is not normal release.

If initialization or background work throws, the coordinated service cancels and cleans up that local attempt, waits `Election.LeaseStandbyInterval` (five seconds by default), and retries initialization within the same valid term. Initialization must therefore be repeatable within one term. `OnLeaderLostAsync(WorkFailed)` means local attempt cleanup, not a shared election loss; other subscribers retain leadership. Successful finite work runs once and keeps its initialized resources until term loss. Loss/shutdown cancels backoff immediately, and no successor starts before prior cleanup finishes. A cleanup exception marks the worker faulted and prevents all later attempts or terms until that worker restarts.

The legacy `IsolationHandlingMode` option and enum are removed. `FastShutdown` previously only logged isolation and never shut down the host. Lease loss now has one lifecycle: cancel leader work and stop renewal when participation is unavailable, while membership retries continue. Applications own any process-exit policy.

Queries read lease observations and join holders to membership records. Current-application leader queries use the exact-resource snapshot overload; they do not enumerate Redis keys. All-leader inventories retain the bulk observation path. Storage errors propagate rather than appearing as no leader. Redis failover may briefly yield duplicate leaders; work with external effects still needs idempotency or resource-side fencing. Stop/drain old discovery workers before migration, select the same backend and scope on every participant, then restart. Old StateStore leader keys and new lease keys do not coordinate with each other; do not roll them side by side. Expired legacy leader keys need no data migration.

## Address and environment metadata

With `AddApplicationModel`, the default client reports `RoleIds` and `DomainNames` from this AppId's selected roles. The legacy singular `DomainName` is populated only when exactly one domain is active. Its AppId must agree with the application model. Per-instance registration and detached snapshots preserve these lists; the merged service view reports the union of observed instance roles/domains, so inspect individual instances during mixed-version rollouts. Domain detail queries, filters, service lists, and domain graphs include every observed owned domain. The inspector reports observed roles independently of process readiness. `GetDomainNames()` includes legacy singular evidence during mixed-version rollout; do not reduce multi-domain membership to the first domain.

Domain metadata comes exclusively from Core's shared [domain catalog](domain-catalog.md). The application model contributes compiled IDs, and the host configures labels once. Registration evidence can contain an unlisted domain; the UI marks that identity without adding it to the catalog. `IServiceDiscoveryCatalogProvider` supplies only predefined applications. Its default implementation reads the complete frozen `Deployment:Applications` map, including applications with an explicit empty role list, and uses each entry's AppName. AppName defaults to its AppId. `ModuleServiceDiscoveryOption.PredefinedServices` can describe additional external applications; names for known deployment applications must agree with the canonical entries. Predefined AppIds must be unique and nonempty; case-only duplicates or collisions with canonical deployment IDs fail composition. This gives current-instance registration, offline application inventory and diagnostics the same names without a second application-name registry.

`DependentSubDomains` and `SetDependentSubDomains` have been removed. `CaptureTopologyAsync()` projects `IApplicationModel.Dependencies` into source domain/role, target domain/role, calling type, and target operation. The dependency UI shows collected static API usages, groups cross-domain pairs, omits self loops, and lets the user inspect their evidence. Its membership counts and service titles still come from registrations. Changing placement or replica count does not change these domain edges. A host without an application model reports unavailable dependency evidence, not an assertion that there are no dependencies. See the [coverage boundary](application-model.md#compiled-api-dependency-evidence); do not infer dependencies from all referenced or registered domains.

`IncludeListeningAddresses` collects the host server's `IServerAddressesFeature.Addresses` into listening-address metadata. To include a process environment variable in full client metadata, add its name to `ModuleServiceDiscoveryOption.MetadataEnvironmentVariables`. `DefaultServiceDiscoveryClientInfo.GetServiceStatus(isHeartbeatInfo: false)` reads those environment variables when constructing the full result; it does not cache them in its constructor. Heartbeat-only results omit this metadata. The registration manager explicitly requests the full result for both initial registration and subsequent heartbeats because each store write replaces the complete registration record.

For a Kubernetes NodePort publication, follow the K8S NodePort publication contract in `$monica-infra-ui` (`references/k8s-workspace.md#publish-the-current-services-nodeport-addresses`). The default output key is `K8S_LISTENING_ADDRESSES`; the K8S initializer does not add it to service-discovery configuration automatically. Preserve or add that key in `MetadataEnvironmentVariables` and, when using the service-discovery UI, in `ModuleServiceDiscoveryUIOption.DisplayMetadataKeys`. Changing the publication output key requires updating both consumers. This external-address metadata is separate from the host server's actual bound listening addresses.

K8S publication runs in the background, so the first registration may precede the address value. The next heartbeat after successful publication reads the current environment and includes the addresses in the full replacement record; later heartbeats continue including them. `ElectionConfig.HeartbeatPeriodSeconds` defaults to `15`. A delayed or failed Kubernetes query does not hold up host startup.

## Captured diagnostics and provider reads

For interactive diagnostics, `CaptureServicesAsync(cancellationToken)`, `CaptureDomainsAsync(cancellationToken)`, `CaptureTopologyAsync(cancellationToken)`, and `CaptureCurrentInstanceAsync(cancellationToken)` return detached evidence in `Res<T>`. Failed reads return an error, rather than a successful empty capture; log details remain on the host. The built-in registration manager propagates registration-enumeration and leader-read failures. A custom manager or predefined-service provider must also distinguish failed reads from successful absence. The store must support registration-key enumeration: a provider that cannot scan keys produces a diagnostic failure rather than an empty registry. The predefined-service provider has no cancellation argument; captures drain its read and then reject canceled results. Domain and topology reads use immutable startup metadata and do not query the registry.

Unexpired `reg:{AppId}:{InstanceId}` entries establish membership in the selected store. The merged view maps them to `Running`; this does not represent a readiness or health probe. Predefined services without registrations remain `Offline`. Their catalog contract supplies identity only, so diagnostics must not invent subdomain or build evidence for them. Version, build, heartbeat and configured metadata displayed at service level come from one observed registration; inspect individual registrations when those values differ.

The independent `service-discovery:<AppId>` lease identifies the stored application leader. A registration's `IsLeader` flag is heartbeat-reported and can lag the lease. Current-host diagnostics show election participation only for `Registry` and `Standalone`; `Worker` does not participate. Local election state and configuration describe the querying host, even while an inspector shows another service. UI-observed disappearances are retained circuit observations, not provider eviction records or a durable cluster history.

Force-delete removes the selected application's leader key; it does not remove registrations or stop a process, and a host may acquire a new lease on a later heartbeat. The existing UI and optional Minimal API authorization remain host-owned. Lease-generation fencing and qualified graceful release are separate backend concerns; a captured UI inspection does not guarantee that leadership remains unchanged when a mutation executes.

The service and domain graphs retain the exact selected service/domain for each cursor-menu opening. Each admitted right-click has its own opening revision, even at the same coordinates; completing an older action cannot dismiss a newer menu or update a retired graph. The native roster Actions remain an equivalent entry point. Domain inspection and navigation to a catalogued subdomain are separate actions: an unlisted domain still supports inspection, but does not gain a catalog route. Integrations use the shared cursor-menu contract in `$monica-infra-ui` (`references/shell-and-access.md`), including document/page coordinates and native menu ownership; these UI lifetimes do not change discovery capture or provider lifetimes.

## Outbound endpoint discovery

Register `monica.AddServiceEndpointDiscovery(...)` to compose `Microsoft.Extensions.ServiceDiscovery` (10.11.0). It uses the native configuration provider against the host `IConfiguration` section `Services`. Call `AddMonicaServiceDiscovery()` once on each participating `IHttpClientBuilder`; this adds native resolution with observation handlers, not another resolver, cache or load-balancing algorithm. Avoid also adding discovery through global HTTP defaults. The registration does not enable state stores, registration, heartbeats, leader election, UI or retry policies.

```csharp
builder.AddMonica(monica =>
{
    monica.AddServiceEndpointDiscovery(options =>
        options.Targets.Add(new("primary", "orders", new Uri("https://orders-primary"))));
    monica.AddServiceEndpointDiscoveryUI(); // Endpoint page only; no membership store.
});
builder.Services.AddHttpClient("orders", client =>
    client.BaseAddress = new Uri("https://orders-primary"))
    .AddMonicaServiceDiscovery()
    .ConfigurePrimaryHttpMessageHandler(() => new SocketsHttpHandler { AllowAutoRedirect = false });
```

Supply addresses through native host configuration, for example `Services:orders-primary:https:0=https://orders.example/gateway`. The library prepends the configured `/gateway` to the request path; the logical URI contains only scheme, service name and optional port. Named endpoint syntax such as `https://_grpc.orders` is supported by Microsoft discovery, but does not implement a gRPC invocation adapter. Hosts own authentication, TLS and optional HTTP policies. Do not replay commands implicitly.

The default `EnablePassThrough=false` requires configured endpoints; absent services produce empty resolution and sends fail. Opt into pass-through for explicit DNS destinations when intended. It returns a DNS endpoint without querying DNS or proving reachability. Configure Microsoft provider options or additional native providers directly through their public extensions, once per host; the facade and HTTP handler use that same provider chain. Refresh reflects the native cache and change tokens, not a forced cache reset. Configuration reload works only if the actual host provider emits reload notifications; environment variables require restart. Role/AppId placement and authority scope remain the application's responsibility. Registered listening addresses are not automatically callable endpoints.

Targets are startup declarations (maximum 256, unique logical URI) used only for diagnostics and safe UI resolution; they do not change application routing. Unknown HTTP destinations can resolve but are not retained. `ServiceEndpointDiscoveryFacade.Capture()` returns detached process-local evidence in `Res<ServiceEndpointDiagnosticsSnapshot>`; check `IsOk()` and `Data`. `RefreshAsync` returns `Res` for the capture operation, with per-target failures represented in the retained snapshot. `RefreshAsync` only resolves declared targets, with a five-second per-target deadline and a thirty-second total budget; it never sends a business or health request. Caller cancellation propagates. The page is `/service-discovery-manage/endpoints`. `AddServiceDiscoveryUI()` includes it alongside membership views; `AddServiceEndpointDiscoveryUI()` can be used independently.

The inspector distinguishes unknown, resolved, empty, failed, timed-out and stale evidence. Failed refresh retains the last successful candidates and their capture time. At most 128 candidates are displayed. Actual selected HTTP destinations are captured inside the native handler, before it restores the logical URI; this does not identify a serving Pod behind a Service. Disable automatic redirects to keep the selected destination meaningful. Address evidence strips user information, paths, queries and fragments; headers and bodies are never retained.

HTTP observations end at response headers. A 2xx observation does not prove successful decoding or business execution. The default history retains at most 200 observations per target for 15 minutes (configurable maximums: 1000 observations and one day). The page reports host/process, capture time, bounded samples and sample p95; missing observations remain unknown. This is not cluster-wide aggregation. Full Invocation results remain owned by [Invocation telemetry](../../monica-infra-messaging/references/invocation.md).

Meter `Monica.ServiceDiscovery` emits `monica.discovery.resolve.duration` and `monica.discovery.http.duration` in seconds, with only declared service names, scopes and bounded outcomes as tags. Hosts enable exporters and storage. Explicit UI resolution contributes to the resolution instrument only, never the HTTP sample count.
