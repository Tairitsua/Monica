# Hosted services

For application unit naming, role placement, queue ownership, scoped operations, and migration from Seeder-started loops, use the hosted-service template in `$monica-application-project-unit-development` (`references/18-hosted-service-template.md`). `HostedService` remains the existing ProjectUnit classification; work items are support types.

The [application model](application-model.md) selects background ownership per resource. Core also supplies a standalone policy when no model is installed. `Application:AutonomousWork=false` holds product background services before construction; disabled owners remain excluded. Native domain/role registrations retain the owner of concrete and factory descriptors through deferred contributions. An opaque factory is never invoked to discover its type. Register product services before or during Monica composition; registrations added afterward are outside that gate and must enforce the same frozen policy.

Core explicitly admits its lifecycle coordinators and modules admit necessary input servers, local diagnostics and bounded explicit-execution infrastructure. Each coordinator still gates its underlying resources. This is not an exemption for every service in a framework assembly. `[ProcessLocal]` applies only to finite initialization whose effects stay in process-owned memory; it cannot authorize external mutations or continuous work. `ModuleDiagnosticsFacade.GetResourceActivations()` reports safe type names, owners, modes and reasons independently of the immutable composition snapshot; held resources are also logged once at host startup.

Use `monica.AddHostedService()` inside the host's `AddMonica(...)` callback when workers need Monica runtime observation. It supplies a registry, runtime observers, checkpoints, and metrics. `MoHostedService` and `MoBackgroundService` report transitions through `RecordState(...)`; they do not replace normal `IHostedService` registration. Register the concrete service through DI and expose that same instance through `services.AddHostedService(sp => sp.GetRequiredService<MyWorker>())` when other services also resolve it. Registering separate singleton instances would make observation and application behavior diverge.

`DefaultMaxHistorySize` is 100, the default background heartbeat interval is one minute, and `FailFastOnStartupError` defaults to `false`. Turning that flag on rethrows start failures and fails the host; leaving it off records/logs them while startup can continue. Use `IMoHostedServiceRegistry` to inspect observed state and heartbeat history; use health checks when the deployment needs a ready/live HTTP contract rather than treating a worker-history view as one. For implementation of a new subclass, read `$monica-development`'s hosted-service reference.

Mediator operations and scoped hosted-service work items share the execution descriptor's method-only transaction declaration. Interface-registered work items use the resolved implementation's mapped method, so place transaction declarations on that concrete method. Use the persistence [transaction contract](../../monica-infra-persistence/references/transactions.md) for overrides and context selection; start/stop lifecycle execution has no automatic UnitOfWork by default.

Mediator requests declare Query/Command intent through `IQueryRequest`/`ICommandRequest` in Monica.Core, normally inherited from the application `IQuery<T>`/`ICommand<T>` contracts. A Query defaults to no new transaction and still joins an active local Shared transaction. An explicit method declaration can request a consistency transaction. Unclassified internal mediator requests retain the Automatic default. Do not register the removed `IReadOnlyRequestConvention` or infer transaction policy from request names or HTTP verbs; see the same transaction contract for outcome propagation and migration.

For a missing worker or a shutdown that does not complete, query `IMoHostedServiceRegistry.GetServices<MyWorker>()` and inspect the exact runtime instance's history. `GetUnhealthyServices()` selects faulted or degraded workers. `MoBackgroundService.StopAsync` records `Stopping`, runs the stopping hook, stops heartbeat observation, and waits through the base background-service stop before recording `Stopped`; a stop exception records `Faulted`. A worker remaining at `Stopping` needs inspection of its cleanup hook and cancellation handling. Use the instance ID when several workers share a type or display name. Implementations must honor the background cancellation token and the separate graceful-shutdown deadline; the registration's startup-failure flag does not define shutdown behavior.

Heartbeat shutdown is cooperative even when the observation worker has not started yet. Await `StopAsync` before disposing the service so the worker can drain, background cleanup can finish, and the remaining stop hooks can complete inside the lifecycle pipeline.

Check `Monica.Core/Modules/ModuleHostedService.cs`, `Monica.Core/HostedService/Abstractions/MoHostedService.cs`, `MoBackgroundService.cs`, and `IMoHostedServiceRegistry.cs` for current registration, queries, and defaults. `tests/Test.Monica.Core/HostedService/HostedServiceRegistryLifecycleTests.cs` covers host-owned lifecycle behavior.
