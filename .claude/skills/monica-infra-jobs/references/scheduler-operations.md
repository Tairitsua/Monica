# Operate scheduled work

Register [JobScheduler](scheduler.md) with a store and scope before exposing operator actions. `JobSchedulerFacade` is the host-facing API for durable definitions, policy, queue, history, and diagnostics. It returns `Res<T>`; check status and data. The facade does not authorize callers: every exposing UI or API owns authorization before each read and mutation, including a policy-conflict reload. `monica.AddJobSchedulerUI()` adds the optional operational workspace and brings the scheduler, shell, and localization modules, but still needs an explicit scheduler store and scope; a Web host must complete `app.UseMonica()` and `app.MapMonica()`.

Trigger arguments and captured execution arguments use MoJson in `$monica-infra-ui` (`references/json.md`) for editing and viewing. Syntax feedback is independent of scheduler admission: optional blank arguments, payload rules and authorization remain owned by the scheduler UI.

Start with `GetRuntimeOverviewAsync()` for this host's configuration, store identity, worker/scheduling readiness, and owner footprint. `GetOverviewAsync()` gives a bounded scope summary. `QueryOperationalSummariesAsync(new JobDefinitionQuery())` or `GetOperationalSummaryAsync(new JobId(ownerKey, jobKey))` shows each definition's recurring cursor, suspension reasons, latest execution, and active queue counts. `QueryExecutionsAsync(query)` returns a bounded page; `GetExecutionAsync(instanceId)` includes append-only attempt history. These views help distinguish an undiscovered definition, a suspended schedule, a waiting execution, and an unhealthy worker.

Runtime's local Scheduling and Worker readiness describe the serving host's last successful cycles. In Manual mode, Scheduling readiness means that its isolated local catalog initialized successfully; no scheduling loop runs. Both flags start false; a false flag can mean initialization or a failed cycle. Preserve the actual latest message, and do not infer a completed cycle from a missing message. In-flight execution count and the configured thread limit belong to this host. The nullable last-owner-work, last-recovery-work and last-cleanup-work timestamps record successful local work, including empty passes; standby-only cycles do not advance them. A cleanup pass may cover only part of the scope. A healthy standby can have no recorded work time. `Configuration.AutonomousWork=false` identifies Manual execution with a fresh local memory store, explicit native execution and no shared scheduler participation. The Runtime identity card and actual provider describe that selected mode.

The information-level `Scheduler history cleanup scan completed` log from `JobSchedulingHostedService` records a completed scan, its scope, worker and next scan time. Partial passes do not emit it. Correlate it with the deployed process and maintenance grant when verifying a complete cleanup cycle; a last-work timestamp alone only proves a successful bounded pass.

The durable owner inventory includes only owners with definition records in the exact scheduler scope, including retained absent definitions. Execution-only owners are outside that population. Definition counts and queued/running execution counts are separate facts. Owner observation now comes from the dedicated owner row; repeating an unchanged manifest does not rewrite each definition. Compare that observation with the accepted runtime `CapturedAtUtc` and `OwnerOnlineThreshold`, which is three times the snapshot-publication interval. An age equal to the threshold is recent, an older observation is stale, and an observation after capture indicates a clock-order discrepancy. The legacy threshold name describes owner publication freshness, not a remote process-health contract. Catalog links encode the complete ordinal owner identity without trimming.

`ManifestPublishedAtUtc` records when the current accepted manifest content was published; repeated observations do not change it. The nullable hash and publication time remain unavailable for legacy owners until their first metadata publication, rather than inferring content changes from old heartbeat timestamps. The Runtime page presents publication and observation separately and makes the accepted hash inspectable.

`GetCoordinatorSnapshotAsync(scope)` observes the exact scope's retained coordinator records and the store-authoritative observation time. It never acquires or renews a lease and excludes fencing tokens. Runtime displays each partition, recorded worker instance and expiry, classifying expiry against that store observation rather than the browser clock. An active grant is not process-health proof; expired grants remain visible. Effective Runtime options include the coordinator duration, store-operation concurrency, reserved lease slots and operation time budget. These configured limits do not establish observed physical connections or throughput.

`IJobSchedulerWorkerInsightProvider` is optional. The built-in ServiceDiscovery provider returns all registered service instances; it does not verify scheduler role, scope membership, owner correlation, or replica capacity. Its `Online`/`Unhealthy`/`Offline` classification concerns heartbeat freshness, and `IsLeader` concerns service-registry election. Preserve absolute heartbeat and registration times. The Runtime UI accepts registry evidence independently of core runtime evidence; its acceptance time is not the provider's classification instant. A successful empty registry, missing integration, failed first read, and retained evidence after a later failure remain distinct.

Component-owned Runtime sessions share overlapping producer reads and start only one automatic loop. Each authorized refresh attempts core and optional registry reads independently; failure in one does not relabel or discard accepted evidence from the other. Denial or authorization-provider failure clears both captures and acceptance times. Retirement cancels and drains admitted reads, timer and subscriber work, and repeated disposal joins actual completion. Subscribers run outside admission locks; a reentrant refresh cannot await the same producer round that is waiting for that subscriber. Cancellation from a retired operation remains cancellation, and unexpected subscriber or cleanup faults remain observable.

Embedded `SchedulerWorkerInsightPanel` consumers must replace the former `CapturedAtUtc` parameter with `HasLoadedWorkerInsight`, `IsWorkerInsightFailed`, and nullable `WorkerInsightObservedAtUtc`, alongside the existing list, registration flag and error. Pass the actual independently accepted registry state. A newer core capture must not make retained registry evidence appear newer or supply invented heartbeat ages.

Interpret the overview's fields according to their separate scopes. Its definitions are a bounded loaded page, so present, type, disabled, and absent counts do not establish the complete scope's definition inventory. Execution-state counts describe the durable scope-wide ledger, including remote owners; Running is a recorded lease state, not proof of this host's worker readiness. Recent records are the newest bounded ledger entries, including skipped occurrences. The trailing-24-hour rate counts all newly created ledger records, including Skipped, rather than only admitted or completed executions. A success share uses only Succeeded and Failed as its denominator and is unavailable when neither exists. Use the Runtime workspace for actual local-plane readiness, and inspect a record before interpreting a review signal as a live incident.

The UI catalog normally starts with present recurring definitions. The overview's `/job-scheduler/catalog?present=false` attention link starts an absent-only view across both job types; resetting that view retains its absence scope and all types. Operators can then select a specific type or return to All types. An additional type filter must not silently hide the definitions that the originating review signal describes. Catalog owner and type facets come from a successful bounded overview read; a failed first read is unavailable, not evidence of an empty inventory. A later failed read may retain the previously accepted facet evidence with a separate error.

Treat owner keys, logical job keys, and execution instance IDs as exact opaque identities. Validate blank values without trimming, changing case, or replacing reserved characters in a valid identity. Encode identities at URI boundaries and preserve them through exact lookup, confirmation, policy save, and native inspection. A catalog `owner` or `present` query change establishes a new owner for state and native dialogs, including when navigation keeps the same page component. No-op parameter renders must not restart that owner, and completion from the retired query must not refresh or mutate its replacement.

The execution ledger's total belongs to its accepted filtered query, not the whole scheduler scope. Creation-time windows include skipped recurring occurrences. Search remains a case-insensitive substring search across job and execution identifiers; an `instanceId` deep link uses that search in the ledger while opening the exact, unnormalized identifier in its inspector. Changes to the raw `states` or `instanceId` route-query identity retire the old ledger and native sessions, including same-document navigation and browser history.

Freeze calendar, search, selected states, page, size, and ordering before awaiting authorization or read serialization. Distinguish a successful zero-record page from a failed first read. A same-intent refresh failure can retain its prior snapshot only with the actual accepted query bounds and observation instant; changed filters, paging, or ordering clear unrelated evidence. Rolling windows advance when admitted, so retained evidence must not acquire a later window label. Authorization-provider faults clear inaccessible data and retain their actual error; an earlier authorized read cannot restore that data after access changes. Cancellation confirms the clicked immutable ID, then separately reauthorizes the mutation and reports the actual durable outcome.

Inspect execution-attempt facts separately. `ExecutionAttempt` records worker claims, while `RetryAttempt` records failures that consumed retry attempts; they are not a progress ratio or a retry-policy denominator. Only a Running record without completion supports duration through the observation instant. A queued retry can retain a prior attempt's start without an end, so waiting time is not active duration. Terminal duration uses the durable `StartedAtUtc` to `CompletedAtUtc` interval. If a queued retry is cancelled before another worker claim, that interval can include retry waiting; it is not guaranteed active attempt time, CPU time, or the sum of attempt durations. Do not manufacture a missing end from retained logs. `GetExecutionAsync` returns complete **retained** history, whereas paged queries omit history. Admission captures the execution template's settings, so later declaration or operator-policy edits do not rewrite an existing execution's captured settings.

Presence means that the definition's owner currently publishes it in the configured scheduler scope. It does not establish local or remote worker health. Exact operational lookup can return an absent persisted definition; its contract, history, and operator policy remain inspectable, and authorized policy updates remain valid. Triggering or running requires a present definition, so the UI must not offer those admission actions for an absent one.

Use `GetExecutionAnalyticsAsync(new JobExecutionAnalyticsQuery { StartTimeUtc = start, EndTimeUtc = end })` for durable-store aggregates in `[start, end)`. `StateTotals` is the current-state cohort **created** in that window; the four terminal outcomes, trend, rankings and duration instead concern records **completed** in it. Success share uses Succeeded / (Succeeded + Failed). Recurring dispatch fulfillment uses RecurringSchedule-origin (Succeeded + Failed) / (Succeeded + Failed + Skipped), so failed work still counts as dispatched; Triggered, RunNow and Cancelled are excluded. An empty denominator makes either ratio unavailable in the UI, whereas zero executed completions per exact window hour is a valid measured rate. None of these facts establishes host readiness or complete lifetime history; retention can remove older records.

Analytics Hour and Day buckets are fixed one-hour and 24-hour UTC intervals anchored to the query start, including zero buckets and a possibly shorter final bucket. They are not calendar-day bins. Today starts at the configured scheduler-calendar midnight; the other UI presets are rolling 24/168/720-hour windows. Ordinary timestamp and interval labels use the shared Clock display policy in `$monica-infra-ui` (`references/time-display.md`), omitting repeated dates and duplicate UTC lines. Only ranges spanning an offset change include endpoint offsets to distinguish repeated wall hours. Scheduler-calendar inputs and Cron previews retain their explicitly labeled schedule timezone. The UI's preset `TimeRange` identifies requested selection immediately, while `LoadedTimeRange` and `LoadedQuery` identify accepted evidence. Query bounds freeze before authorization or serialization; observation is captured after the accepted store read completes. A same-preset failure can retain that evidence, but a changed preset clears it and cannot relabel old results.

Volume and failure shares use all completed outcomes or all failed completions in the selected window, not the displayed Top N subtotal. Longest elapsed results select one measured record for each exact `(OwnerKey, JobKey)`, then apply the global limit. Equal maximum durations select the ordinal-smallest instance ID for that pair, with global ordinal owner/job/instance tie order. Both providers preserve this contract. Queries default to 8 ranked jobs and 10 longest records, with limits 20 and 50; the UI requests 10 for both. Hourly ranges are bounded to 31 days and daily ranges to 366 days.

Application code should enqueue a local typed triggered job through `ITriggeredJobManager`. Using the `RefreshOrderArgs` and discovered job defined in [scheduler](scheduler.md):

```csharp
var instanceId = await triggeredJobs.EnqueueAsync(
    new RefreshOrderArgs { OrderId = 42 },
    delay: TimeSpan.FromMinutes(5), cancellationToken: cancellationToken);
```

For an operator command against a present triggered definition, use `TriggerAsync(new JobTriggerRequest { OwnerKey = ownerKey, JobKey = jobKey, JobArgs = json })`; the definition must be enabled and the JSON must match its declared argument type. `RunRecurringNowAsync(new JobRecurringRunNowRequest { OwnerKey = ownerKey, JobKey = jobKey })` queues an immediate execution for a present recurring definition without advancing its schedule cursor, even when automatic scheduling is paused. Both return an execution instance and accept an optional caller-supplied `InstanceId` for idempotent retries. `CancelExecutionAsync(instanceId, reason)` cancels queued work or requests cooperative cancellation from the running worker.

Code declarations set the initial policy; operators change only policy overrides. Read `GetDefinitionAsync(new JobId(ownerKey, jobKey))`, then call `UpdatePolicyAsync(ownerKey, jobKey, new JobPolicyChange { Overrides = ..., ExpectedConcurrencyStamp = definition.Policy.ConcurrencyStamp })`. A stale stamp returns a conflict; separately authorize the reload before retrying. Freeze the exact target, override replacement, and expected stamp before asynchronous authorization or native confirmation. Selection changes while a confirmation is open must not retarget its accepted batch. `UpdatePoliciesAsync` applies a bounded batch independently and reports each item; remove successful targets from the UI selection while retaining failed ones for review.

Null override fields inherit the code declaration or scheduler default. A present `JobDescriptionOverride` or `JobScheduleBoundaryOverride` whose `Value` is null explicitly clears the corresponding value; preserve that distinction in editors and conflict rebasing. `MaxRetainedHistoryRecords = 0` disables count-based retention rather than inheriting the default or erasing history. Keep timeout precision when editing an existing subsecond value. Schedule overrides cannot change the host-configured cron time zone, and changing prospective policy does not establish a newly synchronized recurring cursor. After conflict, rebase untouched fields against the latest definition while preserving edited drafts; a schedule-kind conflict needs an explicit operator discard or correction.

Component-owned catalog and detail sessions admit initialization, reads, authorization, and mutations before invoking producers. Retirement rejects new work, cancels and drains actual completions, and closes late native dialog references before releasing serialization or interop resources. Start state retirement and native-dialog retirement before joining either: an admitted dialog completion may already be refreshing that state. Follow the shared Blazor lifecycle rules in `$monica-ui-development` (`references/blazor-best-practices.md#22-bound-async-work-to-the-component-lifetime`) for completion reservation, callbacks outside locks, and repeated retirement.

When changing these boundaries, check behavior through real store/facade state tests and native browser actions:

- Query with leading/trailing whitespace, Unicode, and URI-reserved identity characters; exact lookup must neither normalize nor fall back to another owner.
- Retire an old owner/presence query while a cancellation-ignoring read is pending; the new query remains independent, and late rows or confirmations cannot mutate it.
- Delay authorization while a policy revision or selected target changes; use the originally accepted target and stamp, retain conflicts, and apply independent batch successes.
- Revoke authorization between initial viewing and action, including conflict reload; do not read or mutate after denial, and clear inaccessible evidence.
- Distinguish successful zero facets from a failed capture, and verify absent definitions remain inspectable while execution admission is unavailable.
- Freeze a ledger query before delayed authorization, mutate its draft and native table state, and verify each caller receives its own requested page while only the newest admissible read updates shared evidence.
- Retain actual bounds and observation time on a failed same-query refresh; clear rows for a changed query, and prevent a read admitted before access loss from restoring inaccessible evidence.
- Verify running, queued-retry, terminal, missing, and inverted timing facts without invented attempt ends; exact-ID detail reads include retained history and store cancellation outcomes remain distinct from cooperative completion.
- Complete a native dialog open after retirement, make Close or its actual Result fault, and re-enter disposal from a callback; drain actual work and preserve unexpected failures.
- Query actual created/completed boundaries, fixed bucket edges and a partial final interval; trend sums and ratio/rate denominators must match their populations rather than the displayed Top N.
- Give one job two tied maximum-duration records and another owner-scoped job an equal maximum; each provider selects one deterministic record per exact pair before applying the global limit.
- Reverse a requested analytics preset during delayed authorization, retain the prior accepted bounds only for a same-preset failed refresh, and reject stale completion after access loss or retirement.
- Join overlapping Runtime initialization/manual/automatic reads; reenter refresh from a subscriber, then retire while authorization, either producer, or publication is delayed. Observe every actual completion and preserve unexpected callback/cleanup failures.
- Fail core and registry reads independently, distinguishing first failure from accepted empty and retaining each successful capture with its own acceptance time. Denial or provider authorization faults must clear both and reject late cancellation-ignoring results.
- Classify owner observations against the accepted capture at the exact threshold and with a future timestamp; never convert definition-publication freshness into remote worker health.
- Repeat an unchanged manifest and verify its publication time stays fixed while observation advances; accept a changed manifest with the exact prior hash and verify the publication time advances. Query expired coordinator records across distinct scopes and confirm the read neither leaks another scope nor renews a grant.

Protocol upgrades require an explicit all-writer maintenance window for every writer sharing the scheduler tables. Build and verify artifacts first, inventory the scope and all worker/scheduling/trigger/API writers, drain executions, and stop incompatible processes before applying the generated `JobSchedulerDbContext` migration. Preserve identities, policy, cursor positions, execution history and retry/loss budgets. Compare Gate `ActiveCount` to unreleased Running records before restarting; never blindly reset counts to zero.

The schema includes owner-manifest metadata, coordinator grants, and expiry/due indexes. For an existing accepted owner, read `IJobDefinitionStore.GetOwnerManifestHashAsync(scope, owner)` and place that exact old hash in the new host's `OwnerManifestReplacements` only after the stop boundary is established. The first publication in a migrated store establishes its initial hash. Repeating the same accepted manifest requires no replacement setting. Publish a small set of verified new replicas, verify current tokens/cursors and business outcomes, then restore the intended replica counts. Do not use ordinary rolling deployment to mix old serializable/optimistic writers with the new Gate protocol.

Rollback must preserve execution facts after new business side effects occur. Stop and drain new writers before a compatible state-preserving rollback or forward repair. Restoring an old database snapshot alone can replay already completed effects. Scope isolation does not isolate shared physical database CPU, I/O or connection capacity; budget all pools plus migration/monitoring connections on the actual server.
